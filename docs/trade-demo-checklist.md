# 有戏交易演示检查清单

日常只读展示用“有戏-启动”或 `start-local.cmd`，通过 `scripts/check-local.ps1` 确认实际地址。涉及付款、到期和库存写入的完整演示使用隔离后端及浏览器验收，测试替身不调用真实资金、邮件或模型。

| 演示顺序 | 应观察的证据 |
| --- | --- |
| 管理端配置演出、场次和票档 | 用户端能查到上架票档及售卖信息 |
| 用户登录并提交抢票 | 先收到受理状态及请求键，再查询到异步生成的订单 |
| 相同用户用原请求键重复提交 | 返回同一申请，库存只预扣一次，不产生第二笔订单 |
| 隔离环境完成支付并查看结果 | 订单变为已支付，重复通知不会重复处理；同步回跳不直接入账 |
| 另一笔订单保持未付款至到期 | 订单关闭，预占释放，数据库库存和 Redis 配额一致 |

按[项目导读](project-walkthrough.md)讲解受理、落单和恢复三条链路；性能引用[到期对照](performance/expiry-comparison.md)，明确单热点、约 10 次/秒、每组五分钟。真实渠道属于独立验收，见[支付宝沙箱](alipay-sandbox-acceptance.md)和[邮件](smtp-acceptance.md)；不把浏览器测试的替身算成真实渠道回归。

## 本轮验收记录

- 隔离交易专项复测 40 项，38 项通过；用户端、管理端浏览器验收各一项失败。管理端首次复测出现一次页面连接重置，随后单独运行通过。交易 HTTP 闭环、重复受理、到期释放、支付与退款等专项通过。
- 用户端再次运行时 Playwright 通过，后端对已付款、已取消和库存的断言也通过；最后一项客服历史数据库断言失败：预期取消动作关联的两条消息仍存在，实测为 0。不能据此宣称整个用户端验收通过，需核对会话清空范围、动作运行 ID 与消息关联。
- 最终针对用户端复测通过（`target/delivery-conversation-retest.log`）。测试明确区分取消与咨询会话，等待新会话为空再发消息；清空咨询后还能看到原取消卡片，数据库也确认咨询消息为零、取消动作关联的两条消息仍在。管理端与用户端为分别复验，不表述为 40 项在同一次运行中全绿。
- JAR 独立打包成功（跳过测试以验证构建）；未重启日常实例。日志位于模块 `target/delivery-trade-retest.log`、`target/delivery-browser-retest.log`、`target/delivery-package.log`。
