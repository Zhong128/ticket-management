# 热点票档异步建单协调修复

起点：`b2f25d5`。对应[延迟诊断](diagnosis-2026-10-23.md)。本轮处理数据库异步建单的竞争，不调整入口20段Redisson锁、Lua预扣、受理事务或消费者并发，不以100次/秒为门槛。

## 问题与选择

默认建单监听3～10并发，同一票档共享一个`stock_version`。三次新事务条件更新仍冲突后，会进入2、4、8秒等持久化退避。10次/秒诊断中出现约两千次版本冲突和29%～31%的额外建单事件，导致建单等待P95约6.5秒。

本轮选择复用Redisson，在`ReservationServiceImpl.createOrder`的事务外增加票档协调。没有选择全局单消费者，因为不同票档仍需并行；本轮也不引入分片队列协议，避免同时改变路由、消费者拓扑及存量消息处理规则。票档协调锁用于减少无效事务，最终防超卖仍依靠数据库库存充足条件及版本更新，不把分布式锁当作绝对可靠的资金或库存约束。

## 调用与锁序

`SeckillOrderConsumer / OrderRecoveryService → 原OrderService或ReservationService → 读取申请票档 → OrderCreationCoordinator → TransactionTemplate → 原建单事务 → 提交/回滚 → 解锁`

- 独立键为原锁前缀加`order:tier:{tierId}`；按票档划分，两个应用使用相同Redis时互斥，不与入口用户分段键混用。不承诺严格FIFO。
- `tryLock(waitMillis, MILLISECONDS)`不传固定租期，启用watchdog。默认等待2000毫秒，可通过`SECKILL_ORDER_LOCK_WAIT_MILLIS`配置。
- 等锁时没有数据库事务；事务内部保持共享代次屏障、申请锁、库存CAS、建单和Outbox的原锁序与提交边界。外层已有事务时拒绝协调，避免持有连接等待Redis。
- 所有建单入口经过同一Service，涵盖消息与扫描恢复，不在消费者里单独实现另一套扣库存。
- 事务内仍重新读取、锁定申请并核对状态、期限，使用可靠受理的数量和价格快照。重复已建单申请直接返回原订单。
- 原三次新事务CAS重试、数据库库存非负条件、唯一约束、PENDING/HELD释放及支付规则均保留。租约丢失、取消回补等绕过协调的库存变更仍可能引发CAS冲突。

## 暂缓与故障边界

锁忙、中断或Redis不可用抛出`OrderCreationDeferredException`；中断保留线程标记。消费者将其交给现有持久化消息恢复，恢复记录/Outbox提交后才ACK；不能计为普通建单失败并释放预扣。扫描恢复则留到下轮。恢复任务写入失败仍NACK保留Broker消息。

本轮先减少冲突源，没有缩短通用持久化退避、增加无界重试或把重试改为内存任务。消息恢复仍有10次上限和人工状态，数据库扫描继续兜底；严重Redis故障时不保证立即完成建单。等待超过截止时间后仍按原超时规则释放。

锁等待会占用建单消费者，极端热点仍可能占满同一队列的工作线程。不同票档使用独立锁不等于队列流量隔离，后续需要多票档混合和双实例持续测量，再决定是否改成分片路由；本轮不预先承诺该场景收益。

解锁只操作当前线程仍持有的锁；解锁异常记录ERROR和`seckill.order.lock.release.failures`，不把已提交订单当成建单失败。需要核查Redis连接和租约，不强制删除锁，也不保证每次解锁异常都能立即自动恢复。客户端死亡后的租约到期及数据库CAS是安全兜底，不保证Redis故障时可用性不下降。

`seckill.order.lock.wait`及`seckill.order.lock.busy`单独统计建单等待，不污染入口`seckill.lock.wait`。`SECKILL_ORDER_COORDINATION_ENABLED=false`可作同版本对照；它不改变库存协议，关闭时仍使用原CAS。正常运行默认开启。
