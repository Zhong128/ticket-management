# 用户端前端实施计划

目标：使用 Vue 3、TypeScript、Vite、Vue Router、Pinia、Axios 构建 PC 优先、兼容手机的用户端；不做管理端。

## 阶段

1. 基础与浏览：导航、城市选择、首页、搜索列表、演出详情；公开详情和城市接口、最低票价、按城市推荐；近期演出展示数据维护工具。
2. 登录与交易：邮箱注册登录、确认页、幂等抢票、异步建单恢复、支付宝沙箱支付、订单列表与详情。
3. 个人功能：资料、密码、地址、退款记录、AI 客服。
4. 整体验收：手机适配、异常恢复、接口文档、核心流程测试。

每阶段结束报告实际验证与剩余项，确认后继续；不自动提交或推送。用户选择在当前目录开发。

## 设计规范

应用 frontend-design 技能：先设计、检查与票务内容的匹配度，再实现并截图复查。

- 舞台白 #FFFFFF：页面主体；雾灰 #F7F8FA：页面底色；玫红 #EB1761：主按钮；深玫红 #BE104C：强调与可读小字；墨黑 #20212A：正文；次灰 #68707D：次要内容。
- 字体：中文优先 PingFang SC、Microsoft YaHei，西文沿用系统无衬线；标题 24–42px、正文 14–16px，价格使用等宽数字。避免全站相同圆角阴影卡片。
- 1200px 居中、正文左对齐；导航和分类清楚，海报采用 3:4 比例。首页以一张主海报搭配两张演出推荐，详情用左侧海报、右侧选票区。
- 首屏结构：`品牌 | 城市 | 搜索 | 全部演出` → `分类导航` → `主海报推荐 | 两场精选` → `热门现场六列海报` → `分类演出`。
- 设计复核：不采用 SaaS 数字统计和装饰渐变；视觉重点交给演出海报，控件保持安静。手机端海报两列、详情单列；支持键盘焦点与减少动画。

## 展示数据

首批24条，按用户追加要求已扩充至61条近期演出，保留公开来源及海报地址。真实演出名称、城市、场馆与本地演示场次、库存、开售配置分开记录。维护导入工具使用 MyBatis 和事务，只增量添加并重复执行跳过已导入数据，不覆盖已有演出或订单，不清库、不自动迁移。导入清单保留在被忽略的本地输出目录。数据来源不代表本站有真实售票资格。

首页优化：参考实际打开的大麦首页，在主海报下加入图标＋文字的分类导航，按启用分类生成并保留城市；分类推荐采用左侧主推海报、右侧紧凑列表。全国首页最多展示8个有内容的分类区，不混入已结束的早期演出。手机分类采用五列两行，推荐区改为单列。

## 验证与约束

业务访问继续使用 MyBatis。公共接口不泄露草稿，最低票价仅计入启用场次和票档。前端统一处理 Result(code=1)、分页与长整数。请求过期时取消，错误可重试。第二阶段已接入交易页面和接口。原数据库预览仍使用 trade.enabled=false、spring.flyway.enabled=false；隔离容器中验证实际交易链路，页面清楚展示关闭或拒绝受理结果。不会自动迁移原库或启用交易。

运行依赖：Vue、Router、Pinia、Axios、lossless-json、lucide-vue-next；开发测试工具：Vite、TypeScript、vue-tsc、Vitest、Playwright。均是新增前端依赖，不修改后端业务依赖。第一阶段纯逻辑测试使用Node环境，浏览器交互使用Playwright，暂不引入额外组件测试运行时。
